# 2.29 — shared-database facts measured 2026-09-15

Taken under rootless podman on **PostgreSQL 18.4** (`postgres:18-alpine`, the
same major the CNPG operand image runs — `…/postgresql:18.3-system-trixie`)
and **Dragonfly v1.37.0** (`DRAGONFLY_SERVER_IMAGE`, the image the provisioner
pins). These are the measurements [ADR 0066](../adr/0066-shared-database.md)
§7 owed.

**(a) came back against the design and changed it.** That is what it was for.

## (a) The role model — the platform role needs to CREATE what it administers

ADR 0066 §3.1 as first written had CNPG's declarative `managed.roles` create
the group roles and the per-consumer roles, with the provisioner running only
four statements against them. Measured, that does not work, and it fails in
two different places for the same underlying reason: **a `CREATEROLE` role
without superuser may only administer roles it holds ADMIN OPTION on, and it
gets ADMIN OPTION by creating them.**

### What failed

Platform role `apprafter_admin`, `LOGIN CREATEROLE`, not a superuser, a plain
member of the owner group; every role created by `postgres` (standing in for
CNPG):

```
ALTER ROLE claim_apps_web_pg IN DATABASE shd_apps_orders SET ROLE shd_apps_orders;
ERROR:  permission denied to alter role
DETAIL:  Only roles with the CREATEROLE attribute and the ADMIN option on
         role "claim_apps_web_pg" may alter this role.
```

and, when it then tried to create the consumer itself but the GROUP was still
someone else's:

```
CREATE ROLE claim_apps_new_pg LOGIN PASSWORD 'n' IN ROLE shd_apps_orders;
ERROR:  permission denied to grant role "shd_apps_orders"
DETAIL:  Only roles with the ADMIN option on role "shd_apps_orders" may grant this role.
```

A third, smaller constraint appeared once the platform role did create the
group: owning a database as that group additionally requires MEMBERSHIP with
SET, not merely admin —

```
CREATE DATABASE shd_apps_orders OWNER shd_apps_orders;
ERROR:  must be able to SET ROLE "shd_apps_orders"
```

### What works

`apprafter_admin` creates the groups, grants itself membership in them, and
creates the consumer roles — after which every statement in §3.1 succeeds
without superuser:

```sql
-- CNPG's managed.roles creates ONLY this one:
CREATE ROLE apprafter_admin LOGIN PASSWORD '…' CREATEROLE CREATEDB;

-- everything below is the provisioner's, as apprafter_admin:
CREATE ROLE shd_apps_orders NOLOGIN;
CREATE ROLE shd_apps_orders_ro NOLOGIN;
GRANT shd_apps_orders    TO apprafter_admin WITH SET TRUE;
GRANT shd_apps_orders_ro TO apprafter_admin WITH SET TRUE;
CREATE DATABASE shd_apps_orders OWNER shd_apps_orders;

CREATE ROLE claim_apps_web_pg LOGIN PASSWORD '…' IN ROLE shd_apps_orders;
ALTER ROLE claim_apps_web_pg IN DATABASE shd_apps_orders SET ROLE shd_apps_orders;

GRANT CONNECT ON DATABASE shd_apps_orders TO shd_apps_orders_ro;
GRANT USAGE ON SCHEMA public TO shd_apps_orders_ro;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO shd_apps_orders_ro;
ALTER DEFAULT PRIVILEGES FOR ROLE shd_apps_orders IN SCHEMA public
    GRANT SELECT ON TABLES TO shd_apps_orders_ro;
GRANT USAGE, CREATE ON SCHEMA public TO shd_apps_orders;
```

`rolsuper` on `apprafter_admin` reads `f` throughout.

### And the property the whole thing exists for

Three consumers, one shared database:

| actor | action | result |
|---|---|---|
| `claim_apps_web_pg` (rw) | `CREATE TABLE orders …; INSERT` | created — **`tableowner = shd_apps_orders`**, the group, not the creator |
| `claim_apps_api_pg` (rw, a DIFFERENT role) | `SELECT` then `INSERT` | reads `from-web`, writes its own row |
| `claim_apps_rep_pg` (ro) | `SELECT` | reads 2 rows |
| `claim_apps_rep_pg` (ro) | `INSERT` | `ERROR: permission denied for table orders` |

The read-only consumer needed no per-table grant: the single `ALTER DEFAULT
PRIVILEGES FOR ROLE <group>` covered a table created later by somebody else,
which is the reason that line is in the design at all.

### Consequence for ADR 0066

`managed.roles` is used for **one** role, `apprafter_admin`. Group roles,
consumer roles and their passwords become the provisioner's — so password
management for a shared-database consumer moves from CNPG to the provisioner,
which already generates and stores passwords for owned claims. The statement
set stays small and fixed; it is simply larger than four lines.

## (b) Dragonfly — `-@write` does NOT deny PUBLISH

The concern ADR 0066 §3.2 raised, confirmed. On v1.37.0, with the proposed
read-only ACL `+@all -@write -@admin -@dangerous -move -copy -pubsub +sort_ro`:

| command | result |
|---|---|
| `SET k v` | `NOPERM` ✓ |
| `DEL k` | `NOPERM` ✓ |
| `GET k` | allowed ✓ |
| `PUBLISH shd:evt hello` | **allowed** ✗ |
| `SPUBLISH shd:evt hello` | **allowed** ✗ |

A "read-only" consumer could therefore publish into the shared channel prefix
that every other consumer of the same shared cache subscribes to. Adding
`-publish -spublish` fixes it, verified in both directions:

| user | `PUBLISH` |
|---|---|
| ro (with `-publish -spublish`) | `NOPERM` |
| rw (same ACL without them) | allowed |

This is ADR 0042 §2's lesson repeating exactly: `MOVE` and `COPY` were assumed
to be in `@dangerous` and are not. Category membership is verified, never
assumed.

## (c) `DROP EXTENSION` with dependent objects

On PostgreSQL 18.4, with a column default depending on `pgcrypto`:

```
DROP EXTENSION pgcrypto;
ERROR:  cannot drop extension pgcrypto because other objects depend on it
DETAIL:  default value for column h of table dep depends on function digest(text,text)
HINT:  Use DROP ... CASCADE to drop the dependent objects too.
```

`CASCADE` succeeds and **drops the dependent object** (`NOTICE: drop cascades
to default value for column h of table dep`).

**Decision this settles: the platform never issues `CASCADE`.** Removing an
`extensions` entry from a manifest must fail loudly and surface the server's
own `DETAIL`, which names the dependency. A silent `CASCADE` would delete a
column default — user data structure — on a manifest edit whose author was
only tidying a list.

## Method note

The (a) sequence was rebuilt from a clean container after the first two
failures, rather than patched in place: a role graph half-created by
`postgres` and half by `apprafter_admin` would have made the next result
unattributable to either.
