# 2.16d baseline RSS measurement — 2026-08-08

**Provenance:** real Hetzner solo-tier node (`apprafter target add --tier solo`, nbg1), published platform-stack **0.2.47**, `e2e/baseline-memory-walk.sh`. Load profile: platform steady-state + one app (`meas-app`, nginx-hello) with `needs.pg` + `needs.redis` (shared CNPG cluster + ephemeral Dragonfly), ~5 min settle. RSS = kubelet `/stats/summary` `workingSetBytes`. Cluster destroyed + both token projects verified 0.

## Node (corrects the spec's cpx22/8GB/788Mi assumption)
- allocatable.memory = **3814Mi** (~4GB — the solo tier is a ~4GB node, NOT 8GB cpx22; no `kube/system-reserved` set yet → allocatable == capacity).
- kubepods workingSet total ≈ **1096Mi** (matches the 2026-06-17 "~1.07G").
- **k3s.service (~1.5G) is in `system.slice`, OUTSIDE kubepods** (H7 confirmed) — untouched by per-pod requests; must be covered by `system-reserved`.
- Real free-for-more-pods ≈ 3814 − 1096(kubepods) − ~1500(k3s) ≈ **~1.2G** (not the misleading "cap−kubepods=2718Mi").

**App seed** (unknown app; generous-but-present, R4-H5): `requests {cpu:25m, memory:32Mi}`, `limits {memory:512Mi}` (NO cpu limit). The 3Mi nginx confirms 32Mi request is generous for a small app; 512Mi limit is generous for most runtimes without being the lethal-128Mi.

**Backend note:** idle RSS (PG 88Mi, Dragonfly 8Mi) is NOT the sizing basis — under load/at-claim-capacity they grow (Dragonfly to the ADR-0042 ~287MB floor; PG with connections/WAL). Guaranteed limits are sized for load + coherent DB params, not idle.

## Node reservations (from the measurement)
- `system-reserved`: memory=1500Mi (covers k3s.service in system.slice — the ~1.5G observed).
- `kube-reserved`: memory=256Mi, cpu=100m.
- `eviction-hard`: memory.available<100Mi.
- k3s unit `OOMScoreAdjust=-999` (verify k3s doesn't already set it — R4-N4).

## D2 budget-close — **CLOSES** ✅
- allocatable after reservations ≈ 3814 − 1500(system) − 256(kube) − 100(eviction) ≈ **~1958Mi**.
- sum of platform requests ≈ **~800Mi** + backend Guaranteed reserves (CNPG 256 + Dragonfly 320) = **576Mi** + app seed 32Mi ≈ **~1408Mi** < ~1958Mi allocatable.
- **The budget closes with headroom** — no D2 ladder needed (no 2.16f pull-forward, no T1-floor raise, no component trimming). Backends stay Guaranteed. Record: cpx-solo (~4GB) is a viable T1 minimum for the 2.16d baseline.
