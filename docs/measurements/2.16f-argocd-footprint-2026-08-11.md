# 2.16f Argo CD footprint tuning — measurement + finding (2026-08-11)

**Provenance:** real Hetzner solo-tier node (nbg1), `e2e/argocd-footprint-walk.sh` MODE=tuning against the published tuning prerelease **platform-stack 0.2.53-rc.1** (upgraded from stable 0.2.52). Per-container `workingSetBytes` + CPU via the kubelet `/stats/summary` API. Clusters destroyed + both token projects verified 0.

## What the tuning does (delivered + confirmed live)
- `controller.env`: `GOMEMLIMIT=256MiB` + `GOGC=50`; `repoServer.env`: `GOMEMLIMIT=128MiB` + `GOGC=50`.
- `configs.cm.resource.exclusions`: Endpoints/Event, events.k8s.io/Event, EndpointSlice, Lease, metrics.k8s.io/*, cilium.io CiliumIdentity+CiliumEndpoint, autoscaling.k8s.io/VerticalPodAutoscalerCheckpoint.
- `applicationSet.replicas: 0` (7.7.7 has no `enabled` gate).

**Delivery is correct** — live DIAG showed `GOMEMLIMIT`/`GOGC` on BOTH the app-controller StatefulSet and the repo-server Deployment; `helm template argo-cd 7.7.7` with our values renders both. The applicationset-controller pod (43Mi) is gone. Exclusions present in `argocd-cm`. No restarts/OOMKill.

## The numbers (argocd app-controller `workingSetBytes`)

| measurement | app-controller RSS | CPU |
|---|---|---|
| 2.16d baseline walk (fresh, ps 0.2.47) | 359Mi | — |
| this walk — pre-change (fresh, 0.2.52, **no tuning**) | **206Mi** | 15.5m |
| this walk — post-tuning (fresh, 0.2.53-rc.1) | **211Mi** | **4.4m** |
| an earlier run — post-tuning (fresh) | 144Mi | — |

## Finding
- **On a FRESH throwaway cluster the app-controller RSS is noisy (±100Mi) and ~206Mi even WITHOUT any tuning.** A freshly-bootstrapped app-controller is "cold" (small heap); `GOMEMLIMIT=256` does not bind at ~211, and `resource.exclusions` barely helps on a small fresh cluster (few Cilium-identity/event objects to stop tracking).
- **The CPU dropped 15.5m → 4.4m** — a real, observable effect of `GOGC=50` + fewer tracked resources.
- **The memory win is a WORN-IN property.** The tuning's value is capping the app-controller's long-term growth (the 359Mi worn-in bloat → ≤256Mi via `GOMEMLIMIT`), which manifests on a cluster that has been running for a while — not in a 40-min throwaway.

## Consequence (reframe — user-approved 2026-08-11)
- The throwaway walk **gates delivery + no-regression** (env applied, Synced/Healthy, appset 0/0 no pod, exclusions, no restart/OOM, CPU not up). RSS/CPU are **recorded, not gated**.
- The **RSS reduction (359→≤256 cap) is validated on the real worn-in dogfood** — `kubectl top -n argocd` before vs after the tuning lands.
- The `controller.requests.memory` **re-pin is DEFERRED** to the worn-in dogfood measurement; 0.2.53 ships tuning-only with the request left at 288Mi (a safe over-reservation; `GOMEMLIMIT=256` < 288 is a soft heap ceiling below the reservation — no OOM).

## Dogfood follow-up (real landing cluster — the WORN-IN validation)
1. **Before (captured 2026-08-11, dogfood on platform 0.2.46):** `kubectl top pod -n argocd --containers` →
   - **app-controller = 344Mi** (CPU 131m) ← the worn-in RSS the fresh throwaway walk (206Mi) could not show; confirms the finding.
   - repo-server 66Mi + cue-cmp 35Mi; applicationset-controller 26Mi (still running on 0.2.46 — removed by 2.16f); server 27Mi; redis 6Mi.
2. **After (captured ~5 min post-upgrade, cluster still "young"):** `kubectl top pod -n argocd --containers` →
   - **app-controller = 208Mi (CPU 15m)** ← **344→208Mi = −136Mi (−40%)**, CPU 131m→15m (−88%). **208 < the 256Mi GOMEMLIMIT cap → the cap binds and works.** The worn-in memory win the fresh throwaway (206Mi flat) could NOT show is REAL. ✅
   - **applicationset-controller pod GONE** (was 26Mi on 0.2.46) — `applicationSet.replicas:0` applied. ✅
   - repo-server 66→**108Mi**, cue-cmp 35→43Mi, server 27→41Mi, redis 6→4Mi. repo-server is UP (108 < its 128Mi GOMEMLIMIT cap) — likely the young-cluster convergence (helm/git render forks during the just-happened sync); re-check after settle (should drop toward ~66-82). **Watch M2=128MiB under sustained render load.**
   - **This confirms 2.16f's memory-win on the real worn-in cluster** (the throwaway walk gates delivery+no-reg only; this is where the RSS reduction is real).
3. **Re-pin decision (SETTLED measurement 2026-08-11): KEEP 288Mi — a re-pin DOWN is not beneficial.** The settled worn-in app-controller is **~187 → 202 → 227Mi** (3 samples over time, CPU 7-12m — climbing toward the 256Mi GOMEMLIMIT heap cap), NOT the ~166Mi the 5-min-young 208 projected. So a SAFE re-pin (≥ the ~227 working set / the 256 cap) frees only ~32Mi (288→256), and the node is under real memory pressure — `kubectl top node`: **platform-1 = 2696Mi = 137% of allocatable, 1130Mi available, NO swap** — which argues for keeping the app-controller reserved ≥ its working set (protection from eviction), not freeing marginal allocatable. **Decision 5's re-pin is CLOSED as keep-288** (the `GOMEMLIMIT=256 < request=288` is a cosmetic soft-heap-cap-below-reservation — operationally fine, no OOM). repo-server settled 42-114Mi (render-activity variation, < its 128Mi GOMEMLIMIT cap, but close — watch under sustained render load). **The real relief for the node's 137%-allocatable pressure is the 2.16g swap cushion (dogfood retrofit pending), not this 32Mi re-pin.**

## Cold full render: repo-server limit and parallelism (2026-09-22)

The repo-server figures above (66Mi, 108Mi, the settled 42-114Mi) are the **worn-in** working set of a cluster whose Argo CD caches are warm. They say nothing about a **cold full render**, and the container's memory limit has to cover that.

**What a cold render is.** A node reboot, or an Argo CD upgrade that replaces the Redis pod, discards every Argo CD cache at once: the controller's state, the repo-server's disk, and the manifest cache in Redis. After such a restart Argo CD 2.13 does not re-render Applications whose `reconciledAt` is still fresh. It re-compares all of them together when `timeout.reconciliation` (180s) expires. With `reposerver.parallelism.limit` at the chart default of 0 (no limit), the repo-server then runs every Application's work at the same moment: 7-9 `helm pull` / `helm template` child processes of 11-25Mi each, plus a full-history `git fetch` for each git source. The largest single process was a `git index-pack` of the platform repository at ~59Mi. Helm children inherit the repo-server's environment, `GOMEMLIMIT` and `GOGC` included.

**Provenance.** kind (Kubernetes v1.36.4) on rootless podman with a disk-backed root filesystem, Argo CD chart 7.7.7 / v2.13.1 as shipped in platform-stack 0.2.79, 13 Applications: the platform-stack components, a render-only Application that renders the Cilium 1.16.5 chart with the platform's values, and one CUE application. The sampler read the repo-server container's cgroup v2 `memory.stat` `anon` at 5 Hz. `anon` is the memory a disk-backed node cannot reclaim; `memory.peak` also counts page cache. One cold repetition scales the application controller to 0, deletes the Redis and repo-server pods, and scales the controller back to 1. "All compared" is the time from controller start until every Application has a fresh comparison with no `ComparisonError`.

| repo-server limit / `GOMEMLIMIT`,`GOGC` / parallelism | runs | repo-server `anon` peak | concurrent `helm` children | all compared |
|---|---|---|---|---|
| 256Mi / 128MiB,50 / 0 (shipped through 0.2.79) | 3 | 94-148Mi | 6-7 | 190-194s |
| 2Gi / 128MiB,50 / 0 | 4 | 127-158Mi | 7 | 189-196s |
| 2Gi / unset / 0 | 3 | 157-168Mi | 7 | 191-192s |
| 2Gi / 128MiB,50 / 4 | 3 | 90-101Mi | 4 | 191s |
| 2Gi / 128MiB,50 / 2 | 3 | 67-76Mi | 2 | 193-194s |
| 2Gi / 128MiB,50 / 1 | 3 | 67-90Mi | 1 | 200-203s |
| 2Gi / 128MiB,50 / 0, Redis flushed and every Application hard-refreshed | 1 | 179Mi | 9 | 5s |

A limit sweep at parallelism 0 placed the OOM threshold at about 190-200Mi. At 128Mi the repo-server OOM-looped in 2 of 2 runs and never converged. At 160Mi it OOM-looped in 1 of 2 runs, and at 192Mi it was OOM-killed once in 2 runs and recovered. At 256Mi it survived 4 of 4, including the cold start that follows the initial bootstrap. So 256Mi left about 55-65Mi of margin. At parallelism 0 that margin shrinks with every chart or git Application added, because each one adds a child process to the same burst.

**Findings.**

- **`reposerver.parallelism.limit: 2`** halves the cold `anon` peak (67-76Mi against 127-158Mi at 0) and makes it independent of the number of Applications, at a cost of 2-3s until every Application is compared. A limit of 1 is no lower, because one `git index-pack` plus the ~30Mi repo-server process is the floor, and it is 10-13s slower. A limit of 4 lands at 90-101Mi.
- **`GOMEMLIMIT=128MiB` and `GOGC=50` stay.** The repo-server's own heap is ~30-40Mi, far below the cap, but removing both settings raised the cold peak by ~28Mi `anon` (~31Mi `memory.peak`).
- **The repo-server limit rises from 256Mi to 384Mi. The request stays at 66Mi,** because the request is the worn-in figure and scheduling is unchanged. 384Mi is about 2x the worst parallelism-0 peak measured (179Mi) and about 4x the parallelism-2 cold peak (67-98Mi across both runs). A limit reserves nothing on the node.
- The cue-cmp sidecar's `memory.peak` reaches its 128Mi limit on almost every cold render. That is page cache from repository archives being reclaimed, not an OOM: its `anon` stays at 29-37Mi. Its limit is unchanged.

**The shipped combination, re-run on one cluster.** kind as above, the 11 platform-stack Applications as render-only Applications (no automated sync), Argo CD installed with the 0.2.79 values, one cold repetition, then an upgrade to the 0.2.80 values and two more cold repetitions:

| run | repo-server limit / parallelism | repo-server `anon` peak | concurrent `helm` children | OOM kills | all compared |
|---|---|---|---|---|---|
| cold, 0.2.79 values | 256Mi / 0 | 180Mi | 9 | 0 | 200s |
| upgrade to the 0.2.80 values | 384Mi / 2 | 44Mi | 0 | 0 | 183s |
| cold, 0.2.80 values | 384Mi / 2 | 92Mi | 2 | 0 | 205s |
| cold, 0.2.80 values | 384Mi / 2 | 98Mi | 2 | 0 | 200s |

At parallelism 2 the peak is the two heaviest operations running at once plus the repo-server process: the `argo-cd` and `cilium` chart pulls (40Mi and 24Mi) in one run, the platform repository's `git index-pack` (56Mi) in the other. The 180Mi parallelism-0 peak on the same cluster had about 76Mi of `anon` headroom under its 256Mi limit (less the kernel's own charges); under the 192Mi limit of the sweep above, which OOM-killed one run in two, the same peak would not have fit.

The limit and parallelism settings ship in platform-stack 0.2.80. Rolling them out changes an `argocd-cmd-params-cm` key, and the chart's `checksum/cmd-params` pod annotation then restarts every Argo CD pod except Redis once, together (the application controller, server, repo-server and ApplicationSet controller). Redis is not restarted, so this is not a cold render: the restarted controller re-compares every Application at the next 180s tick, and those compares are answered from the Redis manifest cache (the upgrade row above: no `helm` or `git` child process at all).

**Memory-backed root filesystems inflate these numbers.** On a VM whose root filesystem is a tmpfs, every file a pod writes becomes shared memory that is charged to the pod and cannot be reclaimed. This covers git clones, Helm charts, and the ~176Mi `argocd` binary that the `copyutil` init container copies into an emptyDir. On such a VM the repo-server pod needed 386-404Mi. It OOM-looped at a pod limit of 384Mi (256Mi + the sidecar's 128Mi), killed at the pod level while the repo-server process held only 29-37MB of `anon`. At 512Mi (384Mi + 128Mi) it passed 4 of 4 runs. The same chart never OOMed on disk. Size memory limits on disk-backed nodes, and check `memory.stat` `shmem` before trusting a figure from a memory-backed one.
