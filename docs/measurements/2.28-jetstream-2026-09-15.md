# 2.28 — JetStream facts measured on nats-server 2.14.3

Taken 2026-09-15 under rootless podman against
`docker.io/library/nats:2.14.3-alpine` (`-js`), the image
`platform-stack/cue/component_nats.cue` pins deliberately below its own
chart's 2.14.6 default. Client: `natsio/nats-box` (`nats` CLI 0.4.0).

These are the measurements [ADR 0065](../adr/0065-probes-and-jetstream-tuning.md)
§5 owed. Each one is load-bearing for a decision in §2, and none of them is
checkable by any gate in this repository — a wrong answer would ship as a
feature that silently does nothing.

Banner confirming the version under test:

```
[INF]   Version:  2.14.3
[INF] Starting JetStream
```

## (a) The `maxDeliver`-exhausted advisory

**Subject** — exactly as the DLQ design composes it:

```
$JS.EVENT.ADVISORY.CONSUMER.MAX_DELIVERIES.<stream>.<consumer>
```

Observed as `$JS.EVENT.ADVISORY.CONSUMER.MAX_DELIVERIES.WQ2.dur2` for stream
`WQ2`, durable `dur2`.

**Payload** — metadata only. No message body, and **no subject of the original
message**:

```json
{"type":"io.nats.jetstream.advisory.v1.max_deliver",
 "id":"UJan2YMazbCFomwX4RchGI",
 "timestamp":"2026-09-15T17:25:20.037902472Z",
 "stream":"WQ","consumer":"dur","stream_seq":1,"deliveries":2}
```

The `nak` advisory that precedes it on each individual failure carries
`consumer_seq` as well; the terminal `max_deliver` one does not. `stream_seq`
is the only handle back to the message, which is why (b) matters.

## (b) A `workqueue` message survives exhaustion — the body IS recoverable

This is the one that contradicted the expectation it was taken to check. The
assumption going in was that a workqueue message which exhausts redelivery
might be removed, leaving the DLQ advisory pointing at a sequence that no
longer exists. It is not.

With `retention: workqueue`, `maxDeliver: 2`, `ackWait: 2s`, one message
published and NAK'd until exhaustion:

```
=== stream state after exhaustion ===
    "messages": 1
    "first_seq": 1
    "last_seq": 1
=== STREAM.MSG.GET at seq 1 ===
Item: WQ#1 received 2026-09-15 17:25:15 on Subject wq.one

payload-one
```

So `$JS.API.STREAM.MSG.GET` at the advised `stream_seq` returns the body, and
the DLQ story is "metadata in the DLQ, body one fetch away" rather than
"metadata only, body possibly gone". The grant is already in the allow list.

**And the queue keeps moving.** A second message published to the same stream
was delivered and acked normally while sequence 1 sat exhausted:

```
=== does the consumer move on to the NEXT message? ===
body-two
=== stream after the second message was acked ===
    "messages": 1   "first_seq": 1   "last_seq": 2
```

Two consequences worth stating, because neither is obvious and both are
operational:

- An exhausted message is **not** a head-of-line block. The consumer proceeds.
- An exhausted message is **never removed by acknowledgement**, because it is
  never acknowledged. It stays until `maxAge` or `maxBytes` evicts it. A
  workqueue therefore accumulates its poison messages, and its `maxBytes`
  budget has to tolerate that.

## (c) `backoff` vs `maxDeliver` — strictly greater

```
nats: error: Consumer creation failed:
  max deliver is required to be > length of backoff values (10116)
```

Observed with `backoff` of 3 entries and `maxDeliver: 2`; a 2-entry backoff
with `maxDeliver: 3` is accepted. So the webhook rule is
`maxDeliver > len(backoff)` — **strictly** greater, not `>=`. An earlier draft
of ADR 0065 §2.2 said only that the length was "bounded by `maxDeliver`",
which would have permitted the equal case the server rejects.

## (e) Which of the proposed stream knobs 2.14.3 actually honours

All four are honoured and stored. Each was created as its own stream on its
own subject — an earlier run of this measurement collided every stream on one
subject and read `subjects overlap with an existing stream` (10065) as if it
were a rejection of the knob under test.

| knob | result on 2.14.3 |
|---|---|
| `discard: old` | accepted, stored as `"discard":"old"` |
| `discard: new` + `discardPerSubject` | accepted, stored as `"discard":"new"`, `"discard_new_per_subject":true` |
| `compression: s2` | accepted, stored as `"compression":"s2"` |
| `allowDirect` | accepted, stored as `"allow_direct":true` |
| `consumerLimits {inactiveThreshold, maxAckPending}` | accepted and stored **by the server** — set through a raw stream config, since the `nats` CLI has no flag for it. This measured the wrong party; see (f) |

**`discardPerSubject` carries a server-side cross-field rule** the webhook has
to mirror, found by hitting it:

```
nats: error: could not create Stream:
  discard new per subject requires max msgs per subject > 0 (10052)
```

So `discardPerSubject` requires `discard: new` **and** `maxMsgsPerSubject > 0`.

One incidental observation, recorded because it is the kind of thing that
misleads a later reader of this file: the `nats` CLI sets `allow_direct: true`
by default, so every stream above reports it whether or not the flag was
passed. That is a CLI default, not a server one — NACK sends the CR's value,
and a CR that omits the field sends Go's zero value, which is `false`.

## (f) `consumerLimits` never leaves NACK

Measured after the live walk read `consumer_limits: {}` off a stream whose
manifest asked for `maxAckPending: 64` — and the answer is that the server
was never the problem. Row (e) above proves nats-server 2.14.3 honours the
setting; nothing between the manifest and the server sends it.

Source, at the pinned image (`natsio/jetstream-controller:0.24.0`, chart
`nack` 0.35.0):

```
$ grep -c ConsumerLimits controllers/jetstream/stream.go
0
$ grep -n ConsumerLimits internal/controller/stream_controller.go
487:    if spec.ConsumerLimits != nil {
499:        opts = append(opts, jsm.ConsumerLimits(cl))
$ grep -n 'control-loop' cmd/jetstream-controller/main.go
82: controlLoop := flag.Bool("control-loop", false, "Experimental: Run controller with a full reconciliation control loop")
```

`--control-loop` defaults to false, so the binary runs the LEGACY reconciler
and logs `Running in LEGACY mode`. That reconciler builds its `jsm` options
from forty-odd `spec.*` fields and never touches `ConsumerLimits`. The
controller-runtime implementation that does handle it is unreachable without
the flag NACK's own log calls experimental.

Cross-checked the rest of the surface the same way rather than one field at a
time. Every other stream field ADR 0065 §2.1 added — `maxMsgs`,
`maxMsgsPerSubject`, `maxMsgSize`, `maxConsumers`, `discard`,
`discardPerSubject`, `duplicateWindow`, `compression`, `allowDirect`,
`allowRollup`, `description` — appears in the legacy builder, and so does
every consumer field §2.2 added. One dead knob out of the set, and it is now
refused.

**The methodological finding, which is the durable half.** Three gates said
yes: the Application CRD stored the field, the NACK CRD stored it
(`e2e/jetstream-nack-shape-check.sh` asserted precisely that), and NACK's
apiserver call returned 200. Every one of them answers *is this field
accepted*. None answers *does anything read it*. A CRD round-trip is not
delivery, and the only gate that could tell the difference was the walk that
queries the running server. `jetstream-nack-shape-check.sh` now says so in
its own header, so a field added to it next is checked against the reconciler
the chart actually runs — `controllers/jetstream/`, not `internal/controller/`.
